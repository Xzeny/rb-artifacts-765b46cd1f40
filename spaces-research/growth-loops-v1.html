1. Bottom line for the CEO

  1. Rebind's loop runs on a script, not on the app. People search for a job ("show my keystrokes in a tutorial", "one mute key for every meeting app"). The marketplace listing and a working script are what spread. The app is the runtime they install along the way. Every entry point should lead with one script doing one visible thing.
  2. The loop has two install steps, and both lose people. Step 1: install Rebind (Windows admin prompt, macOS Accessibility permission). Step 2: install the script from Marketplace and approve its permission screen. Installing Rebind does not install the script. [Verified-source: mission1\Mission 001-v2\MISSION-001-LOCK.md, "Two-step install"]
  3. Activation means the script did the thing and the person saw it. The overlay showed their keystroke. The mute key muted the call. An install alone is not activation, and neither is the welcome tour. [Lock: "Welcome tour is optional SDK orientation, not Mission 001 activation"]
  4. Today we can only measure as far as download-start. passRefToInstaller is false, and the app does not report first launch with a ref. So no install, script install, activation or share can be tied to a source. There is no honest CPI and this report gives none. [Verified-source: Rebind\campaigns\reddit-seed\landing-pages\LANDING-PAGES-README.md, Config + "Installs (first app launch)"; dossier 05 "Attribution design recorded, not implementation proof"]
  5. The best loop-shaped spaces have $0 entry cost and run on artifacts, not posting: marketplace listings and author pages, an example-script GitHub repo, awesome-lists and package managers, the MCP registry, and show-your-setup cultures where the output itself is visible on screen (Keystroke Overlay in tutorials). Each of these still needs a human GO before any submission.
  6. The one fix that matters most is engineering, not marketing: carry ref through the installer, then log first_launch, script_installed and script_first_run. Without that, every loop below can only be judged by daily install totals against a baseline.

3. The attribution gap, stated exactly

What is built (as design, not proven in production) [LANDING-PAGES-README; dossier 05]
- rebind_landing_visit: ref, ad_group, path, UTMs, timestamp.
- rebind_download: platform and method (installer, PowerShell command or macOS command).
- A session ref joins visit to download. Events go to dataLayer (GTM). The collector endpoint is empty by default.

What is not built
- passRefToInstaller: false. install.ps1, install.sh and the Windows installer do not accept ?ref= today, so the ref stops at the download click.
- The app does not report ref on first launch, so a source cannot be joined to an install.
- No source mentions a script_installed or script_first_run event. [Unknown]

What follows for every loop in this report
- The honest unit is download-start by source. Installs can only be read as daily totals against a pre-campaign baseline (the README's own fallback).
- No CPI, cost-per-install or cost-per-activation can be calculated or quoted. Any such figure would be invented.
- A copied install command or a CTA click is not a completed install [dossier 05]. A completed install is not a script install. A script install is not activation.
- Even the events that exist are unproven: "These code/config notes do not prove collector ingestion or installer/app instrumentation works" [dossier 05].

The fix, in order (a Coding scope, recommended, not requested by me)
1. Installers accept and store ref, then set passRefToInstaller: true (the README documents exactly this).
2. On first launch the app reports ref with its install event.
3. Add script_installed {script_id, ref} and script_first_run {script_id, ref}. The attack plan's "Track first script run" item [§6] is the same idea.
4. A listing-level referrer (for example ?ref= on marketplace URLs, carried into the app) so author and share loops (L1, L2, G) can be credited. [Unknown whether the marketplace supports this]

Until steps 1–3 exist, experiments should be judged on download-start by source plus qualitative first-run checks done by our own testers, not by real users' activation rates.

6. Five loop experiments (hypotheses only, none launched)

Shared rules for all five: nothing goes live without Agency CEO review and Dean's GO. $0 unless Dean approves otherwise. No ads (Mission 001 ads stay HOLD). No organic Reddit. No posting, outreach or submission is drafted for sending. Any later human post opens with Disclosure: I work on Rebind. Activation always means the showcased script ran and the person saw it work. Because of §3, every metric is labeled with what can actually be measured today.

H1. Close the step-2 gap on the listing page (core loop, D)

  • Hypothesis: If the five Mission 001 listings and pages show a "you'll need two steps" strip (install Rebind → then install this script, with the listing URL beside the button and a 10-second "what you'll see" clip), more downloads become script activations than with the current pages.
  • Loop stage: C→D→E.
  • Change tested: page and README copy only. No new traffic.
  • Measure now: download-start by page (exists). Measure properly once instrumented: script_installed and script_first_run per ref.
  • Interim proxy: moderated first-run tests with 5 internal testers per OS. Record where each one stops between download and seeing the script work.
  • Success signal (to set after baseline): a higher share of testers who reach "saw it work" without help. No numeric target until a baseline exists.
  • Stop/bail: if testers still miss step 2, escalate the in-app fix (H2) instead of rewriting copy again.
  • Owner lanes (for CEO to assign): CRO + content-copy; Growth measures.

H2. Arrive-with-intent first run (core loop, D→E)

  • Hypothesis: If the app, on first launch, offers the script the person came for (the attack plan's "first-run recipe"), more installs reach activation than if they must find it in Marketplace themselves.
  • Dependency: needs the ref (or a script id) to survive the installer. This is the same engineering as §3. Blocked until Coding confirms feasibility.
  • Measure: first_launch → script_installed → script_first_run by script id. Not possible today.
  • Guardrails: the person still sees and approves the permission screen. Nothing installs silently. Kill switch shown on that screen.
  • Stop/bail: if offering the script increases cancellations at the permission screen, revert to a plain Marketplace link.
  • Owner lanes: Coding (product) via CEO; Growth defines events.

H3. Visible-output loop for Keystroke Overlay (L1)

  • Hypothesis: Tutorial makers who already need to show keystrokes will keep the overlay in their recordings, and their viewers will search for and install it. Making the listing easy to find from a recording (a short, user-controlled optional caption such as "keystroke overlay: Rebind" that the creator can switch off) increases listing visits from video referrers.
  • Loop stage: E→G→A.
  • What would be tested first: desk research only. Look at what share of public software tutorials show keystrokes and which tools they use. Then, internally, check whether an optional caption is even possible in the script (product question).
  • Measure now: listing visits with video-platform referrers, if marketplace analytics expose referrers [Unknown]. Downloads from guide pages.
  • Guardrails: the caption is off by default or clearly toggleable. No watermark forced on users. No creator contact without comms-creators and consent. The capture limit (Display Capture, not app-window capture) is stated.
  • Stop/bail: if no referrer data exists, park until marketplace analytics are confirmed.

H4. Author loop: give script authors a share kit (L2)

  • Hypothesis: If marketplace authors get a ready share kit (listing URL with a per-author ref, a "requires Rebind (free), two steps" badge, a GIF template and claim fences), authors will promote their own listings and bring installs Rebind's channels do not reach.
  • Loop stage: G→A, with authors as the distribution.
  • Dependency: a listing-level ref that survives into the app (§3 step 4) [Unknown].
  • Measure now: listing visits by author ref, if supported. Otherwise only listing-level visit totals.
  • Guardrails: authors disclose their own interest. No incentive is offered until terms exist. No promised revenue share figures (not quantified in source).
  • Stop/bail: if fewer than a handful of authors are active, the loop has no fuel. Revisit when the publish count grows ("marketplace publishes per month" is already a brief metric).

H5. Directory and registry trickle (L5)

  • Hypothesis: A small set of accurate, permanent listings (Rebind example-script GitHub repo with honest topics, the official MCP Registry, AlternativeTo, one or two awesome-lists) produces a steady, attributable trickle of download-starts at $0, with each listing linking to a specific script page rather than the homepage.
  • Loop stage: A→B.
  • Measure now: download-start with a per-listing utm_content. This works today because it is a landing-page event.
  • Pre-work (research only): read each site's inclusion and self-submission rules, check whether the MCP server meets registry requirements, verify docs before naming any MCP tool.
  • Guardrails: each submission needs GO. Honest one-line descriptions, use-both, no parity, no replacement wording. No referral or affiliate links where rules ban them.
  • Stop/bail: remove or correct any listing that becomes inaccurate (version, platforms). Drop a directory if it sends nothing after a fixed review window set by the CEO.

Experiment priority (recommendation)

  1. §3 attribution fix (prerequisite for judging anything beyond download-start).
  2. H1 (copy-only, no traffic, testable with internal testers now).
  3. H5 (lowest risk, measurable at download-start today).
  4. H2 (biggest likely effect, but blocked on Coding).
  5. H3 / H4 (strongest long-run loops, need product and analytics answers first).
